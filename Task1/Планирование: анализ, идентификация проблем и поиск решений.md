# Планирование: анализ, идентификация проблем и поиск решений

## **Проанализируйте схему и описание системы.** Идентифицируйте существующие и потенциальные проблемные места. Напишите их список.

- **Нет достаточной наблюдаемости внутренних процессов.** <br>
Сайт «Александрит» подключён к Яндекс Метрике. Но с тех пор, как бизнес начал предоставлять оформление заказов через API, данные Яндекс Метрики уже не дают полной картины. <br>
Сейчас ошибки или нестандартные ситуации разбираются со слов клиента: клиенты рассказывают, как что-то пошло не так. Чтобы понять, что случилось, разработчикам и специалистам поддержки требуется очень много времени. <br>
Команда видит, что заказы часто находятся в непонятном состоянии или зависают на каком-то сервисе внутри IT-ландшафта. 

- **Долгая загрузка списка заказов.** <br>
Страница MES со списком заказов долго прогружается, фильтры по статусам и пагинация не помогли.

- **Ограничение горизонтального масштабирования.** <br>
Каждое приложение имеет по одному инстансу. Базы данных имеют один инстанс, который работает на запись и на чтение. Поэтому нам доступно только вертикальное масштабирование, т.е. нет инфрастуктуры для добавления новых инстансов, мы можем только увеличивать мощности уже задействованных машин. В моменты пиковых нагрузок будут появляться узкие места, тормоза, подения, а в моменты спада нагрузки ресурсы будут простаивать.

- **MES не справляется с увеличивщейся нагрузкой** <br>
Открытие API добавило источник запросов на MES. Одновременно увеличилось количество жалоб у тех, кто уже делал запросы на MES.

- **Не ясно текущее состояние RabbitMQ.**
Была озвучена догадка, что сообщения могут просто теряться. 

- **Не достаточно DevOps-инженеров.** <br>
На текущей стадии нам нужно не только поддерживать текущую инфраструктуру, но и мастабироваться. Одного DevOps-инженера не хватит.

- **Не достаточно операторов.**
Операторы работают с заказами. Количество заказов растёт линейно, т.е. с каждым месяцем на одного оператора приходится больше заказов.


## **Разработайте инициативы, которые необходимы для устранения нежелательных ситуаций.** Запишите их в список.

- **Увеличение Observability.**
    - Мониторинг
    - Логирование
    - Трейсинг

- **Добавить кеширование на страницу списка заказов**
Однако актуальный список заказов и их статусов - критично важно для бизнес задач. Поэтому стоит внимательнее отнестись к инвалидации.

- **Разделить процессы записи и чтения**
Базы данных имеют один инстанс, который работает на запись и на чтение. Добавление реплик и балансировки.

- **Добавить инстансы MES API.** <br>
MES API может быть stateless. У нас уже есть внешняя бд. Мы можем добавить API Gateway, он будет заниматься авторизацией и балансировкой запросов на MES API. А инстансы MES API мы будем динамически добавлять или убирать, в зависимости от нагрузки. 

- **Сделать расчёт стоимости асинхронным.** <br>
Расчёт может занимать 30 минут. Это долго, такие операции лучше будет сделать асинхронными. Так же мы можем добавить сервис уведомлений, который будет сообщать о готовности расчёта стоимости.

- **Добавить в команду DevOps-инженеров.**
На текущей стадии нам нужно не только поддерживать текущую инфраструктуру, но и мастабироваться. Один DevOps не вытянет нормальное управление облаком, CI/CD, мониторингом, безопасностью и масштабированием.

- **Проверить настройку RabbitMQ.**
Была озвучена догадка, что сообщения могут просто теряться. А так как RabbitMQ важная часть системы, через которую происходит взаимодействие между сервисами, то стоит проверить текущие настройки: есть ли dead-letter очереди, ретраи и т.д.

    - Количество операторов являются узким местом в пайплайне заказа.
    - Наличие всего одного DevOps-инженера станет узким местом при реализации инициатив.
2. **Увеличеине Observability.** <br>
Сейчас источник проблем мы можем определить только по косвенным признакам. Повышение наблюдаемости поможет с расстановкой приоритетов по другим инициативам. Также это поможет с нахождением проблемы до того, как о них сообщили пользователи.
3. **Добавить инстансы MES API и сделать расчёт стоимости асинхронным.** <br>
Сейчас MES - узкое место в нашей системе. Инстанс MES API только один, а нагрузка на него увеличивается.
