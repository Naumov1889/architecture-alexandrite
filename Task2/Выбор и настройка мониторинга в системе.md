# Выбор и настройка мониторинга в системе

## Мотивация
Сайт «Александрит» подключён к Яндекс Метрике. Но с тех пор, как бизнес начал предоставлять оформление заказов через API, данные Яндекс Метрики уже не дают полной картины. Чтобы начать улучшать систему, нам нужно от чего-то отталкиваться. <br>

Мониторинги дадут количественное представление бизнесовым и инфраструктурным метрикам. Мы сможем точно сказать, сколько человек пользуются нашим сервисом или сколько ресурсов потребляет тот или иной сервис. <br>

Мониторинг — это первая линия обороны. Он даёт объективную картину состояния системы и позволяет быстро находить проблемы:
- **Оперативно находить сбои**. Без мониторинга сбой = пользователь жалуется. С мониторингом сбой = алерт прилетел до жалобы.
- **Находить узкие места**. Видим, где нехватка CPU, куда упираются запросы, где накапливаются сообщения в RabbitMQ.
- **Подкреплять решения данными**. Почему база тормозит? Мониторинг покажет нагрузку, соединения и объём данных.
- **Подготовка к масштабированию**. Нельзя масштабировать вслепую. Метрики покажут, что и когда надо усиливать.


## Выбор подхода к мониторингу
Четыре золотых сигнала - это самая универсальная и полная система метрик для мониторинга любого сервиса. <br>
Этот подход к мониторингу подходит нашей архитектуре: у нас есть API, базы данных и очередь сообщений — везде можно применить эти четыре сигнала.

## Список метрик
### API (Интернет-магазин, CRM, MES)

- Response time (latency)
    - **shop, CRM, MES API**  
    - **Зачем:** Тормоза = потери клиентов и денег  
    - **Ярлыки:** `endpoint`, `метод запроса`

- RPS
    - **shop, CRM, MES API**  
    - **Зачем:** Общая нагрузка на систему  
    - **Ярлыки:** `сервис`

- RPS per user
    - **shop, CRM, MES API**  
    - **Зачем:** Выявление аномальной активности (боты, DDoS)  
    - **Ярлыки:** `пользователь`

- HTTP Errors (500)
    - **shop, CRM, MES API**  
    - **Зачем:** Критические ошибки сервера  
    - **Ярлыки:** `endpoint`

- HTTP Success (200)
    - **shop, CRM, MES API**  
    - **Зачем:** Расчёт error rate  
    - **Ярлыки:** `endpoint`

- Active sessions
    - **shop, CRM, MES API**  
    - **Зачем:** Контроль нагрузки на сервер  
    - **Ярлыки:** `сервис`

- CPU Utilization
    - **shop, CRM, MES API**  
    - **Зачем:** Предотвращение троттлинга  

- Memory Utilization
    - **shop, CRM, MES API**  
    - **Зачем:** Предотвращение крашей  

- Network Traffic
    - **Received (KB):** shop, CRM, MES API  
    - **Sent (KB):** shop, CRM, MES API  
    - **Зачем:** Контроль пропускной способности  

### Базы данных

- DB Connections
    - **shop db, MES db**  
    - **Зачем:** Предотвращение таймаутов  

- Memory Usage
    - **shop db, MES db**  
    - **Зачем:** Предотвращение падений БД  

- Database Size
    - **shop db, MES db**  
    - **Зачем:** Планирование расширения  

### RabbitMQ
- Dead Letters
    - **Зачем:** Выявление проблем в бизнес-логике  

- Messages in Flight
    - **Зачем:** Контроль задержек обработки  

### S3 Storage
- Storage Size
    - **Зачем:** Контроль облачных расходов

## План действий
1. Выбрать стек мониторинга (Prometheus + Grafana).
2. Проставить метрики в код API и MES через готовые либы для связи с prometheus.
3. Настроить экспорт RabbitMQ и баз данных в Prometheus (готовые экспортеры).
4. Поднять базовую Grafana-дашборду: RPS, ошибки, задержки, очереди.
5. Настроить алерты на критические метрики через prometheus:
    - RabbitMQ:
        - dead-letter-exchange > 0 — сразу алерт.
        - in flight > 1000 — варнинг.
    - API (shop, CRM, MES):
        - HTTP 500 > 1% за 5 мин — алерт.
        - Response time > 3s — варнинг.
    - Базы данных:
        - connections > 80% от лимита — варнинг.
        - Memory Utilization > 85% — алерт.
    - Инстансы (EC2):
        - CPU > 90% 5 минут подряд — алерт.
    - Диски:
        - Size of db > 80% — варнинг.
